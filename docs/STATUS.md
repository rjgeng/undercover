# Status

The claims pilot in `docs/PLAN.md` is built: all six phases are done. The harness in `docs/PLAN_HARNESS.md` is under way: phases 1 to 5 of 6 are done.

## Running it

- `npm run dev` starts the backend on port 8000 and the dashboard on http://localhost:5173.
- `uv run -m backend.seed` rebuilds the database from `data/`, putting every claim back in the queue.
- `uv run -m agent` starts a run of the queue agent, capped at the number of waiting claims, and `uv run -m agent --cap 5` caps it at five. It prints each claim's line as it comes back, then the run's summary, or says no claims are waiting. `uv run -m agent CLM-1001` works one claim with a fresh claim agent and prints one line, like `CLM-1001: approve $420.00, paid`. Both use the real model through OpenRouter, DeepSeek V4.1 Flash by default.

## Built

- `backend/`: SQLite database seeded from `data/` (never `data/evals/`), at `undercover.db` or the path in `UNDERCOVER_DB`, created on startup when missing. Read operations: `health`, `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `list_handlers`, `list_steps`, `get_instructions`, `read_section`. Workflow operations: `start_claim`, `record_step`, `record_decision`, `pay_claim`, `sign_off_claim`. A claim moves from waiting to in progress to decided, or to waiting for sign-off when an approval pays over the limit in `company.json`. `pay_claim` refuses such a payout with a 403 until a handler signs off, and signing off pays it. Seeding also stores the claims manual. `read_section` serves one numbered section of the policy wording or the manual. The agent's instructions are in `backend/instructions/`: `queue.md` for running the queue and `claim.md` for working a claim, written from the wording and the manual. `get_instructions` serves both, with the claim instructions followed by the contents of the wording and the manual. A test checks that every operation follows the API rules.
- `backend/` runs, for the harness: `start_run`, `get_latest_run`, `take_claim`, `update_todos`, `finish_run` and `fail_claim`. A run has a cap on the claims it can take and a to-do list. It can't finish while it has missed a waiting claim within its cap. Starting a run stops any run left unfinished and puts its claims in progress back in the queue. A claim that fails goes back to waiting, and the second time to `needs_handler`. Only a claim in progress can fail, so nothing is decided twice. The queue agent uses them.
- `agent/`: `run(claim_id, thread_id)` starts the claim, fetches its instructions from the backend and works the claim with six tools named after backend operations: `get_claim`, `get_policy`, `get_claim_history`, `read_section`, `record_decision` and `pay_claim`. It records every tool call, tool result and message as a step, and each section it reads as a `read` step. `work_claim(claim_id)` runs it and reports on the claim in one line. If anything fails, or the agent ends without a decision, it records the failure with `fail_claim`, so the claim goes back in the queue, or to a handler the second time, and is never left in progress. A claim that fails after its decision keeps the decision. The model is `deepseek/deepseek-v4.1-flash` at low reasoning effort, or `MODEL_NAME`. A model call times out after 60 seconds, and `ModelRetryMiddleware` retries it twice. The agent reaches the backend at `UNDERCOVER_API`, or `http://127.0.0.1:8000`. A claim agent can take 60 LangGraph steps.
- `agent/queue.py`: the queue agent. `run_queue(cap)` starts a run and gives the queue agent four tools: `list_claims`, `update_todos`, `work_claim` and `finish_run`. `work_claim` takes the claim into the run, within its cap, then hands it to a fresh claim agent and returns its one-line report. The run id reaches the tools through LangChain's runtime context, never from the model. The run gets 20 LangGraph steps for each claim it can take.
- `dashboard/`: the queue (`/`), with the latest agent run, its to-do list and its summary, counts by state, including Needs a handler, and a line per claim. A claim in full (`/claims/:claimId`), with its policy, earlier claims, the decision and payment, what the agent read, the agent's steps as it works, including its reads and failures, the number of failed attempts, and a sign-off form for a held payout. The agent's instructions (`/instructions`) in two parts, running the queue and working a claim, read only. The queue and a claim page refresh every two seconds. Styled to `BRAND.md` in light and dark mode.
- `e2e/`: tests of the three pages, the agent's steps appearing on a claim page, a handler signing off a held payout, the queue page following a run's to-do list to its summary, a claim that fails twice, and what the agent read. Playwright runs its own backend on port 8001 with `e2e/undercover.db`, and its own dashboard on port 5174, so it can run next to `npm run dev`.

## Last live run

On November 3, 2026, `uv run -m agent CLM-1001` with `deepseek/deepseek-v4.1-flash` approved CLM-1001 for $420.00 and paid it, in 11 seconds. It read 4 sections of the wording and 8 of the manual, each shown as a `read` step.

The pilot's run, on September 27, 2026: `uv run -m agent` with `openai/gpt-6-luna` worked all 25 claims in 2 minutes 47 seconds: 17 approve, 5 decline and 3 refer. Three approvals were over $1,000 and waited for sign-off (CLM-1003, CLM-1008 and CLM-1011), and every other approval was paid its payout. These decisions have not yet been scored against the handlers' decisions in `data/evals/`.
